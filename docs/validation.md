# 검증 기록

기록 기준일: **2026-10-22 (KST)**. 사용자 직접 확인과 AI 도구로 수행한 자동 검사를 구분했습니다. 이번 코드 점검의 변경 내용은 [최종 점검 보고서](code-audit-final-2026-10-22.md)에 정리했습니다.

## 직접 사용한 결과

사용자가 배포 사이트 접속, Slack 계정 연결, 테스트 DM과 실제 예약 메시지 수신을 확인했습니다. 언어·테마는 휴대전화 2대·태블릿 1대·개발 PC에서 동작을 확인했고, 포커스 처리 보완 후 문제 PC에서도 실제 마우스 선택이 정상 반영되는 것을 확인했습니다. 수정 전 이벤트 순서는 직접 기록하지 않았으므로 원인 추정과 해결 결과를 구분합니다.

별도 실서버 QA에서 임시 계정의 가입·프로젝트·일정·할 일·계정 변경·삭제 흐름을 확인한 기록도 있습니다. 해당 QA에서는 Slack 승인·발송을 실행하지 않았습니다. 조건과 결과는 [실서버 QA 기록](qa-live-2026-10-22.md)을 참고합니다.

## 남은 확인

### Slack 오류와 취소 재시도에서 확인할 부분

관련 처리는 코드에 구현되어 있습니다. 다만 모의 검사에서 확인한 결과와 실제 배포 서버에서 자동 작업이 실행되는지는 구분합니다.

| 처리                                  | 현재 구현·화면에서 확인할 수 있는 것                                                                                                                              | 추가로 확인할 것                                                                                                        |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 예약 요청의 결과가 불확실함           | `UNKNOWN` 등으로 보관하고 중복 예약을 막습니다. 리마인더·일정 상세에서 오류와 상태를 보고, 해당 상태의 `상태 확인`으로 Slack 대기 예약 목록과 대조할 수 있습니다. | 실제 권한 철회·응답 지연·Slack 장애에서도 저장 상태가 유지되고 재확인되는지                                             |
| 탈퇴 중 예약 취소 실패 또는 시간 부족 | 채널·예약 ID 등 재시도 정보를 DB에 남기고 계정 데이터를 삭제합니다. 예약 ID 자체를 모르는 미확정 상태는 탈퇴 전에 확인하도록 막습니다.                            | 실제 실패 상황에서 계정 삭제와 취소 작업 보관이 함께 처리되는지                                                         |
| 탈퇴 후 서버가 예약 취소 재시도       | 정기 작업 API와 Vercel의 매일 12:00 KST 실행 설정이 있습니다. 취소 성공 또는 이미 없는 예약으로 확인되면 작업을 지우고, 실패하면 다음 시도 정보를 기록합니다.     | 배포 환경의 `CRON_SECRET`·실행 설정, 실제 호출·오류 기록, DB의 시도 횟수·다음 시각·작업 정리 여부, Slack 예약 취소 결과 |

**현재 화면에는 탈퇴 후 남은 취소 작업을 조회하는 기능이 없습니다.** 어떤 예약의 취소가 남았는지, 서버가 언제 몇 번 재시도했는지, 어떤 오류가 났는지, 결국 취소가 완료됐는지, 정기 작업이 실제로 실행됐는지를 화면에서 확인할 수 없습니다. 운영자가 Vercel 실행 기록과 DB의 `slack_cancellation_jobs`, Slack 예약 목록·DM을 함께 점검해야 합니다. 이 확인은 아직 수행하지 않았습니다.

정기 작업은 정해진 보관기한이 지난 작업도 삭제합니다. 따라서 DB에서 작업이 사라진 사실만으로 취소 성공을 단정하면 안 됩니다. 취소 성공을 영구 보관하는 이력 화면도 없습니다. 실제 메시지 게시·읽음·푸시 수신 확인은 별개이며 현재 구현된 예약 목록 대조로 증명할 수 없습니다.

구현 근거는 `server/api/account/index.delete.ts`, `server/db/migrations/004-operations-and-account-deletion.sql`, `server/api/internal/slack-cancellations.get.ts`, `server/services/reminders.ts`, `vercel.json`입니다.

### 그 밖에 남은 확인

- 운영 배포 반영 확인. 이번 빌드 통과가 배포 완료를 뜻하지는 않습니다.
- 대량 데이터의 응답 시간·크기 측정과 목록 페이지네이션.
- 운영 DB에서 항목 변경·알림·연결 변경·탈퇴가 겹치는 요청의 경합 검증.
- 새 빈 DB에서 전체 구축 절차의 실검증.

이번 점검에서는 실제 DB 접속·마이그레이션·사용자 변경·Slack 발송·취소·배포를 실행하지 않았습니다. 이전 캘린더 점검의 운영 DB 읽기 연결도 실패해 실데이터 확인은 하지 못했습니다. 실행 준비는 [로컬 개발 안내](local-development.md), 과거 결과는 [추가 점검 보고서](code-audit-followup-2026-10-22.md)를 참고합니다.
