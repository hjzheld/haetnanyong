## 방법과 안전 범위

- 실제 Chrome 브라우저와 실제 API를 사용했습니다. 모의 API 테스트가 아닙니다.
- 별도 임시 계정으로 회원가입하고 그 계정이 생성한 프로젝트·할 일·일정만 변경했습니다.

- Slack OAuth 승인과 실제 메시지 발송은 수행하지 않았습니다. 앱 기능 코드를 수정하거나 재배포하지 않았습니다.

## 통과한 범위

### 실제 API 및 인증

- 비로그인 상태의 보호 화면 접근 시 로그인으로 이동.
- 비인증 API 요청 401 응답.
- 회원가입 화면에서 이메일·비밀번호 입력 후 가입 및 세션 생성.
- 닉네임 미입력 시 자동 생성.
- 프로젝트 생성·이름/색상 수정, 보관·복원. 프로젝트 상세 화면 열림.
- 개별/프로젝트 소속 할 일 생성, 날짜 범위 유지, 우선순위·제목·완료 상태 수정.
- 시간 일정 및 종일 일정 생성, 날짜 유지, 시간 일정 수정.
- 시작일보다 이른 종료일 및 잘못된 색상 입력 거절.
- 닉네임 변경, 비밀번호 변경, 로그아웃, 변경한 비밀번호로 재로그인.
- 로그인한 상태에서 로그인 URL 접근 제한 및 없는 URL의 404 안내.
- 테스트 데이터 삭제 및 테스트 계정 탈퇴.

### 실제 화면 조작

- 모바일 플랜 등록 모달에서 새 프로젝트와 할 일 동시 생성.
- 프로젝트 내 할 일 링크에서 상세 진입 → 수정 화면 → 저장 → 완료 처리.
- 플랜 모달의 일정 탭에서 시간 일정 생성.
- 입력한 `2026-10-23 14:00 KST`와 저장된 일정 시각이 일치하는지 확인.
- 등록한 일정이 캘린더에 표시되는지 확인.
- Slack 미연결 상태에서 일정 상세의 알림 설정을 누르면 마이페이지 Slack 영역으로 이동.
- 일정 상세에서 삭제 확인 후 삭제하고 조회 API가 404를 반환하는지 확인.

### 반응형 및 도움말

1440 / 768 / 390 / 320px에서 다음 9개 화면을 검사했습니다.

- 홈, 프로젝트 플랜 목록, 개별 플랜 목록, 캘린더, 리마인더, 마이페이지.

각 화면의 페이지 전체 가로 넘침 여부, 도움말 버튼 개수, 모달 열기 및 Escape로 닫기를 확인했습니다. 캘린더 등 내부 영역의 의도된 가로 스크롤은 페이지 전체 넘침과 구분했습니다. 화면 캡처도 생성했습니다. 이 검증은 모든 콘텐츠 길이·모든 브라우저에서 CSS 문제가 없다는 보장은 아닙니다.

## 발견 사항

### QA-01 — 캘린더의 일정 등록 버튼이 등록 폼 대신 목록으로 이동

- 우선순위: 중간(P2, 사용자 흐름 불일치).
- 재현: 로그인 → 캘린더 → `+ 일정 등록` 클릭.
- 실제: `/plans?tab=individual&kind=events`의 개별 일정 목록으로 이동. 등록 모달은 열리지 않음.
- 기대: 등록 버튼이면 일정 작성 화면 또는 일정 탭이 선택된 등록 모달이 바로 열려야 함.
- 영향: 사용자가 플랜 등록을 한 번 더 눌러야 하며, 기존에 기대했던 캘린더 → 작성 → 뒤로가기 흐름을 해당 버튼으로 시작할 수 없음.
- 권장: 캘린더에서 일정 모달을 바로 열거나, 플랜 페이지로 이동할 때 일정 등록 모달을 자동으로 여는 명시적 상태를 전달. 목록 이동이 의도라면 버튼 문구를 `일정 목록 보기`로 변경.
- 재현 화면은 당시 로컬 임시 캡처로 확인했습니다. 캡처 파일은 저장소에 포함하지 않았습니다.

### QA-02 — 이메일 인증 비활성화와 맞지 않는 안내 문구

- 우선순위: 낮음(P3, 안내 정확성).
- 위치: 마이페이지 → 내 정보.
- 실제 문구: `이메일은 인증된 계정 식별자라 현재 변경할 수 없고, 닉네임만 수정할 수 있어요.`
- 문제: 이메일 인증 없이 회원가입 가능한 현재 동작과 `인증된`이라는 표현이 맞지 않음.
- 권장: `이메일은 로그인에 사용하는 정보로 현재 변경할 수 없어요. 닉네임만 수정할 수 있어요.`
- 확인 화면은 당시 로컬 임시 캡처로 확인했습니다. 캡처 파일은 저장소에 포함하지 않았습니다.

### QA-03 — 회원가입 화면의 도움말 누락

- 우선순위: 낮음(P3, 이전 도움말 적용 요구와의 차이).
- 실제: 회원가입 화면에는 도움말 버튼이 보이지 않음.
- 권장: 가입 정보·선택 닉네임·로그인 안내를 담은 도움말 버튼을 공개 인증 화면에도 배치.
- 당시 캡처의 실패는 자동화가 이전 가입 버튼 문구를 찾은 것이며 회원가입 자체의 결함이 아닙니다. 실제 가입은 수정된 선택자로 통과했습니다. 캡처 파일은 저장소에 포함하지 않았습니다.

## 오탐과 검증 한계

- 첫 자동화에서 가입 버튼을 `회원가입`으로 찾았으나 실제 배포 문구는 `가입하고 시작하기`였습니다. 테스트 선택자 문제이며 사이트 버그로 집계하지 않았습니다.
- 첫 API 점검에서 `GET /api/projects/:id`를 가정했지만 해당 단일 조회 API는 현재 구현 목록에 없습니다. 이 요청 실패를 프로젝트 기능 결함으로 간주하지 않았습니다. 생성·수정·보관·복원·프로젝트 상세 화면은 별도로 확인했습니다.
- 프로젝트 할 일 링크에는 날짜도 포함돼 정확한 제목만으로 링크를 찾는 테스트가 처음 실패했습니다. 실제 href 선택자로 재검증한 상세·수정·완료는 통과했습니다.
- 두 개의 서로 다른 로그인 계정 사이의 객체 접근 격리는 미검증입니다. 비로그인 차단만 확인했습니다.
- Slack 실제 계정 승인, OAuth 콜백 성공, DM 수신, 연결 후 예약/취소/상태 재확인, 예약 알림의 프로젝트 배지 실데이터 표시는 미검증입니다.
- 이메일 실제 발송, 여러 서버/동시성, 부하·장애 주입, 장기간 예약 및 iOS Safari/Android 실기기는 검증하지 않았습니다.
- 따라서 이 결과를 전체 기능 100% 정상 또는 전체 보안 검증 완료로 해석하면 안 됩니다.

## 남은 Slack 검증 방법

사용자가 본인의 브라우저에서 테스트 계정으로 로그인한 뒤 마이페이지에서 직접 Slack 로그인과 권한 승인을 해야 합니다. 자동화 브라우저와 사용자 브라우저는 세션 및 OAuth state가 다르므로 승인 URL만 다른 브라우저로 옮기는 방식은 사용하지 않습니다.

승인 후 다음 순서로 추가 확인할 수 있습니다.

1. 마이페이지의 연결 상태와 테스트 DM 수신 확인.
2. 미래 시각의 일정에 몇 분 뒤 알림 예약 후 실제 DM 수신 확인.
3. 별도 알림을 예약하고 취소한 뒤 취소 완료 및 미발송 확인.
4. 상태 재확인과 중복 예약 방지 확인.
5. 프로젝트 소속/개별 일정의 리마인더 배지 유무 확인.

Slack 비밀번호·클라이언트 시크릿·봇 토큰은 공유하지 않습니다.
