# 프론트·백엔드 최종 점검 — 2026-10-22

기존 미커밋 변경을 포함한 현재 코드의 화면·입력·캐시·세션·소유권·일정/할 일 API·Slack 예약 보호·공통 UI를 점검했습니다. 이 문서는 이번 점검에서 새로 고친 내용과 검증 결과입니다. 이전 수정 전체를 이번에 새로 구현한 것으로 집계하지 않았습니다.

## 발견한 문제와 수정

| 영역                 | 문제                                                                            | 수정                                                                                          |
| -------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 일정 수정            | 화면에서는 지난 예약으로 보여도 DB의 `SCHEDULED`가 계속 활성으로 판정되어 409   | 지난 예약만 Slack 대기 목록과 재대조한 후 DB 활성 상태 재검사                                 |
| Slack 연결 변경·해제 | 같은 지난 예약 때문에 정기 작업 전까지 연결 변경이 막힐 수 있음                 | 공통 `hasActiveReminders`로 같은 재대조 경로 사용                                             |
| 프로젝트 항목 색상   | 프로젝트 상세에서 수정할 때와 별도 상세→수정 화면의 잠금·응답 색상이 다름       | 상세 API에서 프로젝트 색상 상속, 별도 수정 화면도 잠금·`color` 전송 제외. 개별 색상 수정 유지 |
| 홈 도움말            | 실제 오늘 일정·3일 이내 마감과 다른 ‘오늘과 내일’ 설명                          | 현재 표시 범위로 수정                                                                         |
| API 명세·검사        | 기본 명세의 재예약·메시지 규칙과 일부 브라우저 캘린더 기대값이 이전 동작에 머묾 | 현재 재예약·고정 머리말·본문 길이, 보관 프로젝트 포함 정책과 링크명으로 정정                  |

수정 파일은 `server/services/reminders.ts`, `server/utils/slack-connection.ts`, `server/api/events/[id].patch.ts`, 일정·할 일의 `[id].get.ts`, `server/utils/openapi.ts`, `app/components/workspace/ItemEditor.vue`, `app/components/common/PageHelp.vue`와 관련 검사 스크립트입니다.

## 보호 조건

`hasActiveReminders`는 미래 예약이나 `UNKNOWN` 같은 미확정 상태가 있으면 기존처럼 차단합니다. 지난 `SCHEDULED`만 남으면 채널별 대기 목록을 요청 안에서 재사용하고, 예약이 남았거나 조회가 실패하면 보호를 유지합니다. 재대조 후 DB도 다시 확인합니다. 외부 호출 예산은 15초이며 DB를 포함한 전체 응답 시간 보장은 아닙니다.

이 변경은 예약 정리 조건을 맞추는 작업입니다. 실제 메시지 게시 확인 기능을 구현한 것은 아닙니다. 해당 기능은 README의 향후 계획으로 남겼습니다.

- 타입 검사와 최종 Nuxt/Nitro 프로덕션 빌드를 통과했습니다.
- 빌드된 서버에서 모의 API를 사용해 등록·재시도·보관/복원, 색상 상속, 완료 처리 성공·실패, 캘린더 이력·종료 표시, 도움말·뒤로가기, 언어/테마 포커스, 모달 잠금·중첩·복원, 모바일 고정 바·약관 링크를 확인했습니다. 스크립트별 최종 결과는 [검증 기록](validation.md)에 모았습니다.
- 홈·프로젝트의 완료 체크박스는 실패 응답에서도 정상 복원됨을 재현 검사로 확인해 기능 코드는 바꾸지 않았습니다.
- 문서 25개의 상대 링크 58개에 누락이 없었고 형식 검사도 통과했습니다. 현재 문서에서 실제 로컬 환경변수 값·개인 PC 절대 경로는 발견하지 못했습니다. 생성된 OpenAPI 31개 경로·41개 작업도 실제 라우트 파일과 대조했습니다.
- `check-item-colors.mjs`는 실제 DB를 사용하는 검사이므로 실행하지 않았습니다. 해당 스크립트에서 SELECT 문자열을 찾는 취약한 인덱스만 정정하고 새 상세 색상 검증은 모의 검사로 수행했습니다.

개발 서버 일부 실행에서 초기 스크립트 로딩 타임아웃이 있어 최종 결과는 프로덕션 빌드에서 다시 확인했습니다. 빌드의 초기 파일 접근 제한은 권한 검토 후 같은 명령으로 완료했으며 별도의 배포 설정 변경은 하지 않았습니다.

## 문서 정리

문제 PC의 사용자 직접 확인 결과, 색상 상속·지난 예약 보호, 실제 서비스 모듈 위치, 로컬 환경변수 안내 위치와 검사 명령을 현재 코드에 맞췄습니다. 과거 점검 보고서는 당시 결과로 보존하고 최신 기록을 연결했습니다. README는 사용자 승인에 따라 이용 안내를 합쳤고 기존 말투로 발송 여부 확인 계획을 추가했습니다.

## 남은 범위

운영 DB·Slack에 접속해 검증하거나 사용자 데이터를 변경하지 않았고 배포도 실행하지 않았습니다. 전체 동시 요청의 직렬화·운영 경합·대량 데이터·외부 장애·실제 취소 큐 복구·새 DB 구축은 별도 검증이 필요합니다.
